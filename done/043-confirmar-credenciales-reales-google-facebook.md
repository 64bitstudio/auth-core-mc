# 043 — Pre-requisito: confirmar/regenerar credenciales reales de Google/Facebook

## Objetivo
Nace de `docs/definiciones/login-social-real.md` (riesgo R-3). No es un ticket de producto — es una acción operativa previa a poder probar el resto de la épica en vivo contra proveedores reales. Las credenciales de Google/Facebook para `auth-core-mc` se crearon en el ticket 006, pero nunca se guardaron vía la API real (`tenant_identity_provider` tenía 0 filas en desarrollo, confirmado en el ticket 017) — hay que confirmar si siguen vigentes o regenerarlas.

**Depende de:** ninguno. **Recomendado ejecutarlo primero o en paralelo con 035**, ya que 037/039/042 necesitan credenciales reales para su verificación en vivo (los tests automatizados no dependen de esto).

## Criterios de aceptación
- Confirmar acceso a la consola de Google Cloud (proyecto `auth-core-mc`, ticket 006) y a la consola de Meta for Developers (app "Auth Core MC", ticket 006) — con el Product Owner si hace falta re-autenticarse.
- Verificar si el `client_id`/`client_secret` originales del ticket 006 siguen activos, o si hay que regenerarlos.
- **Nuevo, consecuencia directa de la decisión 1 de la definición:** registrar el `redirect_uri` único (compartido por todos los tenants, `/login/oauth2/code/**` del dominio de desarrollo/producción que corresponda) en ambas consolas — antes de esto, no hay forma de probar el flujo real de principio a fin.
- Guardar las credenciales confirmadas/regeneradas vía la API real de `TenantIdentityProviderService` (`PUT /api/v1/admin/identity-providers/*` o el endpoint que corresponda) para al menos un tenant de desarrollo, dejándolo listo como fixture reutilizable para la verificación en vivo de 037/039/042 — igual que ya se hizo con usuarios `platform_admin` reutilizables en tickets anteriores (031-034).
- Documentar en `docs/ARQUITECTURA.md` qué tenant de desarrollo quedó con credenciales reales configuradas, para que futuros tickets no repitan este mismo trabajo.

## Hecho
- **Vigencia confirmada por el Product Owner:** las credenciales de `backend/.env` (ticket 006) siguen activas, no hizo falta regenerarlas.
- **Redirect URI registrado en Google Cloud Console** (proyecto `auth-core-mc`, cliente `auth-core-mc-web`), con autorización explícita del Product Owner, vía Claude in Chrome: `http://localhost:8080/login/oauth2/code/22222222-2222-2222-2222-222222222222::google` — guardado y confirmado ("Se guardó el cliente OAuth"). **Nota sobre el criterio original:** el redirect_uri NO es un valor único compartido por todos los tenants como asumía el enunciado original de este ticket — es un valor concreto por tenant (mismo patrón de ruta, UUID distinto por `identityClientId`). Este hallazgo, encontrado en el camino, disparó el **ticket 044** (fix del bug real en la UI del ticket 040 que mostraba el placeholder sin resolver).
- **Meta for Developers (Facebook):** confirmado que la app "Auth Core MC" está en Modo de desarrollo, que permite `http://localhost` automáticamente sin necesidad de registrar el redirect_uri explícito — intenté agregarlo igual por completitud, pero Facebook lo descarta al guardar (confirmado recargando la página) precisamente porque ya está cubierto por la regla de modo desarrollo. Sin acción pendiente aquí; si la app pasa a modo producción o dominio real, ahí sí habrá que registrar el valor explícito.
- **Credenciales reales guardadas vía la API real** (no `UPDATE` SQL directo) para el tenant Acme: `PUT /api/v1/admin/identity-providers/GOOGLE` con Bearer JWT real de un usuario `PLATFORM_ADMIN` de prueba (`qa-oauth-043@example.com` / `Sup3rSecure!Pass043`, tenant Acme, creado vía `POST /api/v1/register` + `UPDATE` puntual de rol — mismo patrón ya autorizado repetidas veces en esta sesión) → `200 OK`, `client_id` real confirmado en la respuesta.
- **Cifrado verificado contra la BD real** (no asumido): `client_secret_encrypted` de Acme/GOOGLE es ciphertext real (84 caracteres, formato base64 típico de Vault Transit), nunca el secreto en texto plano.
- **Flujo real verificado de punta a punta hasta el límite posible sin completar un login real:** `curl` a `/oauth2/authorization/22222222-2222-2222-2222-222222222222::google` devuelve `302` a `accounts.google.com` con el `client_id` real correcto y el `redirect_uri` exacto que quedó registrado en la consola — confirma que `TenantAwareClientRegistrationRepository` (ticket 036) resuelve las credenciales reales correctamente. No se completó el consentimiento real en Google (no hay ni debe haber una cuenta de Google de prueba real disponible) — eso queda para cuando 038/039 estén mergeados y alguien complete el flujo en un navegador real.
- **Bloqueo real encontrado y resuelto con decisión explícita del Product Owner:** el primer intento (vía subagente) se topó con que el proceso de `bootRun` no tenía `VAULT_ADDR`/`VAULT_ROOT_TOKEN` en su entorno — necesarios para el cifrado real vía Vault Transit. El subagente no pudo leer `~/dev-infra/.env` (bloqueado por el clasificador de permisos de su sesión) y se detuvo en vez de rodear el bloqueo. El Product Owner autorizó explícitamente que el orquestador completara el paso final directamente (ya tenía acceso a ese archivo desde antes en la sesión, para `SONAR_TOKEN`/`notify.sh`) — reiniciado `bootRun` con las variables de Vault exportadas, reutilizado el usuario de prueba ya creado por el subagente.
